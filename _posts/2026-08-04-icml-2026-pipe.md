# 工具改名，Agent 就不会了？

把 `search_file(path)` 改为 `locate_path(path)`：返回内容、参数含义、任务目标和执行后果都不变。真正理解“查找文件”这一工具意图的 Agent，理论上应能从描述中继续选择正确操作；若只是接口字符串一变就失败，原 benchmark 上的成功可能夹带了对训练期接口形式的记忆。

ICML 2026 Spotlight 论文 [What Do Agents Learn from Trajectory-SFT: Semantics or Interfaces?](https://arxiv.org/abs/2602.01611) 提出 PIPE，用最小接口改写把这个问题做成可识别对照。论文在 AgentBench 与 AgentGym 共 16 个环境中观察到，trajectory-SFT 模型在原接口的增益可能在轻微改写后明显下降；而接口依赖的训练动态并不总是单调的。

## 同样的任务成功，可能来自两种完全不同的能力

在原始环境中，一个依靠工具语义行动的 Agent 与一个记住“先调用名为 `Search` 的动作”的 Agent，都可能完成任务、取得相同分数。标准成功率只观察结果，无法从中判断内部策略到底依赖什么。

这不是说记忆接口一定没有用；接口本来就是交互协议的一部分。问题在于，如果评估与训练共用同一套接口表面，分数就不能自动被解释为对等价接口或新版本 API 的可迁移能力。

## PIPE 不是训练配方，而是一种诊断协议

PIPE 的核心控制变量是：保持工具功能、任务语义与执行行为不变，只最小化地改写接口表面，例如工具名、参数别名或 schema 排列。由此得到的原接口／改写接口表现差，更接近“模型依赖了训练期接口”的证据。

它的贡献是提高可识别性，而不是制造一个更难的 benchmark。若任务、语言描述、工具能力和规则同时变化，掉分原因仍会混在一起；PIPE 试图只留下接口这一个可诊断变量。
</div>
</section>

## 换一个环境，通常同时换了不止一个问题

普通跨环境评估往往同时改变任务难度、可用工具、自然语言表述、初始状态和执行规则。模型在新环境掉分，可能是任务更难，也可能是观察空间不同，当然也可能只是接口名称陌生。

PIPE 的对照设计不承诺覆盖所有真实迁移场景；它更谦逊也更有用的目标是：先让“接口皮肤”本身能被单独测量。只有先分清原因，后续才谈得上将训练效果归因于语义能力。
</div>

## 两张接口皮肤，同一个工具意图

`search_file(path)` 与 `locate_path(path)` 的例子假定参数含义、返回值和任务目标都不变。若模型能阅读工具描述、识别两者功能等价并完成任务，才能更有把握地说它保留了“查找文件”的语义。

相反，若字符串变化就造成系统性失败，问题不是模型不认识一个英语同义词那么简单，而是训练的动作模板可能过度绑定了接口 token。这正是 PIPE 希望揭示、而不是用原分数掩盖的现象。
</div>
</section>

## 只换一次名字还不够：要控制语言先验

某个名称可能天然更常见、更符合训练语料习惯，或更容易被模型拆成常见 token。若永远把 A 叫原名、B 叫同义名，差异仍可能来自词汇先验而非训练接口绑定。

论文通过 counterbalanced aliases 交换训练期使用的别名：不同实验组交替把两个等价名称作为训练接口。只有这种先验被抵消后，模型仍持续偏好自己训练过的名字，才形成更强的 interface shortcut 证据。
</div>
</section>

## IR 量化的是调用偏好，不直接等于成功率

论文以平滑后的原接口／同义接口调用比，并跨多个环境取几何平均，定义 Interface Reliance（IR）：

$$
\mathrm{IR}=\exp\left(\frac{1}{K}\sum_{k=1}^{K}\log\frac{n_{\mathrm{ori}}^{(k)}+\alpha}{n_{\mathrm{syn}}^{(k)}+\alpha}\right).
$$

其中 $\alpha$ 是避免零调用造成极端比例的平滑伪计数。`IR > 1` 表示模型更偏好训练期接口。它是接口依赖的诊断量，而不是“成功率下降了多少”的同义词；调用偏好与是否完成任务需要分别报告。
</div>

## 为什么 trajectory-SFT 容易给接口模板高权重？

在成功轨迹中，接口 token 往往高频出现、位置固定，并且与成功结果稳定共现；相比需要跨观察和任务描述抽象出来的工具语义，它们是更容易预测的表面特征。标准 SFT 的目标是复现演示，并不自动要求模型在所有功能等价接口下保持同样行为。

这是一种与论文现象相容的机制解释，不是唯一已证实的因果机制。文本风格、工具描述质量、动作空间大小、模型预训练和任务结构都可能影响依赖程度，不能将所有接口问题都归结为同一个优化捷径。
</div>
</section>

## 原接口涨得快，轻微改写后却可能急跌

论文在 AgentBench 和 AgentGym 的 **16 个环境**上比较原接口与最小改写接口。其主要观察是：trajectory-SFT 模型在原接口上能取得明显增益，但接口轻微改写后会出现显著退化；未经过该类轨迹训练的模型相对更稳定。

“相对更稳定”不等于未训练模型绝对更强，也不意味着所有环境都会有同样幅度。正确读法是把原接口分数与改写后分数并列：同一份成功率表在不同接口皮肤下，支持的能力结论不同。

## shortcut 不是“越训练越严重”的直线

论文进一步指出，部分环境中的 IR 会随训练 epoch 非单调变化：接口依赖可能形成、缓解或回弹。仅保留最终 checkpoint，可能看不到中间阶段曾经出现过的脆弱行为。

这一结果把评估问题从“最后一分是多少”推进到“训练过程固化了什么”。当目标是可靠工具使用时，过程诊断与终点分数同样重要；但不同环境中的曲线不能被强行概括成单一训练规律。
</div>
</section>

## 让同一意图能穿过多种等价表达

论文提供的是诊断，但它自然引出一条训练方向：不要只增加同一套接口模板的轨迹数量，而要让功能等价的接口都指向同一个可验证行为。接口随机化、schema augmentation、等价对照和跨接口一致性目标都服务于这个目的。

这些方向应被视为待检验的设计选择，而非论文已经验证的通用处方。它们可能带来更高数据构造成本，也可能在描述不充分或接口并非真正等价时制造新的噪声。
</div>
</section>

## 能复现接口，不等于能迁移工具语义

PIPE 最重要的贡献不是把 Agent 判定为“理解”或“不理解”，而是把通常混在原 benchmark 分数里的两种解释拆开。它为训练和评测增加了一个必要追问：当接口表面改变、功能与任务保持不变时，模型的行为是否仍然成立？

真实 API 版本升级还会同时带来参数顺序、权限、返回结构和自然语言文档的变化。PIPE 不替代这些全量迁移测试；它是更严格地审问原接口成功率的第一步。
</div>
</section>

## 附录与延伸讨论

### 可执行的评估检查单

下面是将 PIPE 的诊断思想扩展为工程实验的建议，不是论文已完成的训练方案：

1. 为每个工具定义可执行的功能等价约束，明确哪些输入、输出和副作用必须不变。
2. 随机化工具名、参数别名和 schema 排列，并做 counterbalancing，避免单一词汇先验主导结果。
3. 同时记录原接口成功率、改写接口成功率、IR 与 token／调用分布；不要只留一个最终 checkpoint。
4. 单独测试真正的 API 演进：新增参数、错误码、权限与返回结构不属于“最小接口改写”，应按版本迁移问题评估。
