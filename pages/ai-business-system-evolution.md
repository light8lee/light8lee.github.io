# AI 业务系统从零建设与持续进化路线

> 从没有现成标注数据的新场景出发，借助通用 LLM 快速建立业务能力，通过真实反馈形成数据闭环，再将稳定能力压缩到低成本模型，并按业务需要发展为 workflow／Agent，最终形成可验证、可回滚、可持续适应的进化机制。

## 一、整体思路：先建立正确性，再积累、固化和扩展能力

这里的“从零建设”，指从零建设业务判断标准、数据资产、执行流程与评估体系，通常不意味着从零预训练基础模型。

最初没有标注数据，可以通过提示词工程（Prompt Engineering，简称 PE），把业务定义、少量人工确认的案例和通用 LLM 的能力结合起来，先在线下验证，再逐步用于线上和离线批量处理。运行过程中收集误伤、漏放、人工改判和未知问题，持续修正判断边界。

当部分能力在真实数据上已经稳定，就可以通过监督微调（SFT）和蒸馏，让较小模型承担高频、明确的问题。通用 LLM 转向疑难判断、补充证据和处理新问题。如果任务需要动态选择工具和调整执行路径，再引入 Agent，并逐步优化其提示词、记忆、技能、工具和运行环境。

积累可靠的任务轨迹与反馈后，可以开展 Agent SFT、失败状态纠正学习，以及条件成熟时的 Agent 强化学习（RL）。最终，再把 Agent 探索出的稳定能力沉淀成规则、workflow、skill 或专用模型，继续降低成本。

**阶段推进的依据是当前瓶颈和验证结果，不是数据量、上线时间或技术复杂度。** 并非每个业务都必须走到 Agent RL；能够稳定、经济地解决业务问题，就是当前阶段的合理终点。

### 1. 阶段总览

| 阶段 | 核心问题 | 主要产出 | 下一阶段的触发条件 |
| --- | --- | --- | --- |
| 0：定义业务契约 | 什么算对，错了代价多大？ | 判断标准、种子评测集、指标与人工出口 | 典型样本可以被一致解释，分歧有处理机制 |
| 1：LLM 冷启动 | 没有训练数据，怎样先解决问题？ | LLM + PE 基线、结构化结果、试运行链路 | 离线达到试运行门槛，线上可追踪、可暂停 |
| 2：数据与边界闭环 | 如何知道哪里错，并有效修正？ | 真实样本池、可信标签、错误分类与回归集 | 稳定子任务已被识别，错误可以归因 |
| 3：能力蒸馏与分流 | 如何在质量约束下减少成本？ | 轻量模型、知识外置、快慢分流系统 | 单次判断的局限开始阻碍多步任务；否则持续优化本阶段 |
| 4：Workflow 与 Agent | 如何可靠完成多步业务任务？ | 工具契约、执行状态、workflow／Agent 及轨迹 | 执行可观测、结果可验证，重复失败值得系统优化 |
| 5：非参数化进化 | 如何让经验成为可复用改进？ | 版本化 PE、memory、skill 与候选发布机制 | 存在高质量轨迹，权重层面的行为瓶颈仍持续存在 |
| 6：Agent SFT 与纠正学习 | 如何学会业务操作并从错误中恢复？ | 适配业务 harness 的模型与恢复数据 | 监督学习后仍存在可探索的策略优化空间，且环境与奖励成熟 |
| 7：Agent RL | 如何提高受约束的任务收益与路径质量？ | 经验证的决策策略、奖励与环境版本 | 有稳定、高频的成功路径可以进一步压缩 |
| 8：能力再压缩与持续适应 | 如何让成熟能力更便宜，让新问题继续被发现？ | 固化能力、漂移监控、淘汰与再训练机制 | 新分布或新瓶颈出现时，返回对应阶段 |

阶段之间存在依赖，但并非严格串行：数据与评估贯穿全程；知识外置、缓存和 PE 优化可以很早开始；简单 workflow 也可以在冷启动时引入。Agent SFT 不要求先完成所有非参数优化，能力再压缩也不必等 RL 完成。

### 2. 五条贯穿全程的建设主线

| 主线 | 持续回答的问题 |
| --- | --- |
| 数据 | 样本是否代表真实业务，标签是否可信，是否遗漏未知错误？ |
| 知识 | 规则是否清晰，证据是否充分，知识是否过期？ |
| 模型 | 哪些能力可以稳定承担，哪些需要升级处理？ |
| 执行系统 | 工具、状态、重试与恢复是否可靠？ |
| 评估 | 改进是否真实、可解释、可泛化，是否值得上线？ |

## 二、阶段 0：定义业务契约与最小评估底座

### 关注什么

先让人能够一致地判断任务，再让模型学习。没有现成标注集，不等于可以没有判断标准。

以客户咨询与业务办理为贯穿示例：需要分类时，可将“需要人工处理”定义为正类。误报是将可自动解决的问题错误转给人工，漏报是将需要人工处理的问题留给 AI。答复是否正确、客户诉求是否遗漏，应另外评估，不能只看转人工分类是否正确。

### 怎么做

1. 明确任务对象、输入范围、可获得证据和输出结构，区分模型判断与实际处置动作。
2. 写清正例、负例、例外以及证据不足的处理方式。允许“无法判定”“需要补证据”“需要人工复核”。
3. 由业务专家确认一批真实或贴近真实的种子案例，覆盖常规、边界和困难情形；记录判断依据与分歧。
4. 为误伤、漏放、人工复核、处理时延和成本定义指标。不要只用总体准确率掩盖稀有正类的失败。
5. 预先确定离线验收、试运行、扩大流量和回滚条件。阈值由业务代价与可承受风险确定，不套用通用数值。

### 产出与验收

产出一份业务判断契约、一套种子评测集、一份指标定义和人工处理流程。业务方与工程方能够解释同一个案例为什么可以自动处理、需要人工或无法判断；暂时无法一致的案例被显式标记，不强行制作确定标签。

### 何时进入下一阶段

当核心任务有明确的成功标准、种子案例可复核、失败有出口，就可以进入 LLM 冷启动。若人之间的分歧主要来自政策含糊，应先修定义，继续调模型不能消除这类分歧。

## 三、阶段 1：用通用 LLM 与少量案例完成冷启动

### 关注什么

用尽可能少的前置训练成本，验证通用模型是否能够完成核心任务，并建立可记录、可回放的最小业务链路。

### 怎么做

1. 在相同样本、提示词、工具和推理条件下比较候选底座，确定能力基线。先识别可达到的质量，再做成本取舍。
2. 将 PE 拆成任务定义、判断依据、边界条件、少量示例、输出格式和无法判定条件。
3. 要求结果包含标签、证据引用、适用规则及升级原因。记录可核查的依据，无需依赖冗长的内部推理文本。
4. 如判断依赖业务知识，接入版本化规则或检索资料，避免模型凭通用知识猜测当前政策。
5. 先做离线回放，再做影子运行：处理真实请求但不直接改变业务处置。达标后逐步开放有限自动处理范围。
6. 同时建设离线批处理链路，支持批次标识、失败重跑、断点续跑与幂等，保证重跑不会重复产生业务动作。

线上与离线应使用同一套可追溯的判断契约，但运行策略可以不同：线上优先满足时延与降级要求；离线可以使用批处理、更多证据和更充分的复核。二者指标分开报告。

### 产出与验收

产出一个可复现的 LLM + PE 版本，保存输入、输出、规则版本、模型版本、异常、时延和成本。离线质量达到阶段 0 定义的试运行门槛，格式错误、超时和无法判定都能进入明确出口。

### 何时进入下一阶段

当系统能够安全试运行并持续记录真实反馈，就开始数据闭环。若模型在证据完整的核心案例上仍不稳定，应检查底座能力、任务拆分或业务可判定性，不急于扩大流量。

## 四、阶段 2：建立数据闭环，按根因修正判断边界

### 关注什么

让运行产生的数据能够支持改进。关键不只是收集更多样本，而是知道样本从哪里来、标签是否可靠，以及错误由什么造成。

### 步骤 1：同时建设代表性采样与定向采样

| 样本来源 | 用途 | 注意事项 |
| --- | --- | --- |
| 随机或分层抽样的真实流量 | 估计线上整体表现 | 保留抽样概率；非均匀采样时按设计估计总体指标 |
| 模型分歧、边界附近样本 | 提高标注价值 | 不能直接用于估计全量错误率 |
| 新渠道、新类型、异常输入 | 发现未知问题和分布变化 | 建立新类型标签，不只套用旧错误分类 |
| 误伤、漏放、投诉和人工改判 | 修复已知问题 | 反馈有选择偏差，也可能延迟或不准确 |

不能只采集升级给 LLM 或人工的样本。还要持续抽查已经被小模型或规则自动完成、转交的样本，否则自信错误很难进入改进闭环。

### 步骤 2：建立标签可信度与来源记录

利用规则、历史处置记录、业务知识与 LLM 生成候选标签，优先复核冲突样本。多个来源可能共享同一种错误，不能把多模型一致直接当成真值。弱监督可以组合有噪声的标注源，但仍需独立验证标签质量。[1]

每条数据至少记录样本来源、采样方式、时间、候选标签、最终标签、依据、复核状态及业务规则版本。区分未标注、伪标签、人工确认和真实结果反馈。

训练集、提示词优化集和最终测试集应隔离。按时间、用户、实体或相似样本簇划分，避免重复内容跨集合泄漏。合成样本适合补充边界和稀有情况，不能替代真实流量上的效果验证。

### 步骤 3：先归因，再决定改什么

| 错误根因 | 应采取的动作 |
| --- | --- |
| 标签错误或业务定义冲突 | 修订标注或业务契约 |
| 缺少图片文字、上下文或外部事实 | 改善数据获取、OCR 或检索 |
| 规则表达含糊、示例不充分 | 优化 PE 和示例 |
| 政策或知识过期 | 更新外置知识与生效版本 |
| 阈值或分流不合适 | 调整阈值、校准或升级策略 |
| 模型能力不足 | 更换底座、训练或拆分任务 |
| 工具或执行失败 | 修复接口、状态、重试和恢复 |

### 步骤 4：用边界实验修复误伤和漏放

对于由规则定义导致的误伤，可以增加适用前提、排除条件或例外；对于覆盖不足导致的漏放，可以补充表达形式、风险类型或适用情形。

例如，“提到退款就转人工”会把仅查询退款进度的客户也转给人工，应区分查询进度与需要人工裁定的争议。如果漏转来自没查到订单异常状态，应补订单查询能力，而不是继续堆叠提示词。

每次修订同时检查错误样本、相邻正例和相邻反例。误伤与漏放可能互相转移，因此要同时测两侧边界。随着规则增长，定期去重、检查冲突与优先级，并拆分为结构化模块。

### 产出与验收

产出可追溯样本池、可靠标签集、错误归因表和专项回归集。每次修改都有明确假设，能够解释改善了哪类问题、是否损害邻近类型。

### 何时进入下一阶段

当某些高频子任务在真实数据上表现稳定、标签质量可接受，并且成本成为明确瓶颈，可以进入能力蒸馏。数据闭环继续运行，不因训练启动而结束。若业务边界仍频繁变化，应优先稳定定义和知识管理。

## 五、阶段 3：知识外置、能力蒸馏与快慢分流

### 关注什么

在既定质量约束下扩大低成本自动处理范围。优化对象是端到端业务成本，而不只是单次模型调用价格。

### 步骤 1：先做轻量降本与知识分层

优先检查缓存、批处理、上下文压缩、重复请求消除、规则前置，以及 embedding 或简单分类器是否足够。缓存要绑定业务规则版本和必要输入，政策变化时能够失效。

经常变化的事实、政策与例外放在外部知识库；稳定识别能力、结构化输出和操作习惯适合进入模型权重。外置知识可以早于本阶段建设。

### 步骤 2：对稳定子任务进行 SFT 与蒸馏

1. 选取已经被验证可靠的教师输出和人工确认数据，而不是复制全部 LLM 预测。
2. 覆盖常见正负例、边界负例、困难样本、正确弃答及正确升级处理。
3. 训练后按业务类型分别评估，并与当前生产基线比较。
4. 验证学生模型自己的能力边界。教师能稳定处理的题型，不意味着学生同样可靠。

通过教师生成并经验证的数据训练学生，是蒸馏的一种工程实现；SFT 是训练方式，数据来自 LLM 本身不保证蒸馏质量。

### 步骤 3：建立带退出机制的路由

```text
业务请求
  → 规则或有效缓存：范围明确时直接处理
  → 轻量模型：在已验证的能力范围内处理
  → 强 LLM：解决疑难判断或补充证据
  → 人工复核／暂缓决策：仍无法可靠判断
```

“快思考”指低成本模型承担稳定识别，“慢思考”指较强系统承担复杂判断；它们是系统分工，不意味着每条请求都要串行经过所有模型。

路由应结合独立验证表现、分类型阈值、校准分数、分布异常、证据完整度和模型分歧。模型自报置信度不能直接作为可靠概率，强 LLM 也不是绝对正确的兜底。

### 产出与验收

产出轻量模型、路由策略、知识库版本和成本收益报告。共同检查误伤、漏放、自动处理覆盖率、升级率、时延及总成本。

总成本应包含各级推理、工具、人工复核、训练维护和错误处置成本。满足质量约束之后，再比较成本下降是否足以抵消训练与维护投入。

### 何时进入下一阶段

如果主要任务仍是一次分类或抽取，可以长期停留在本阶段。只有当业务需要查证、多步操作、状态跟踪或动态决定下一步时，才转向 workflow／Agent。数据量增长本身不是升级理由。

## 六、阶段 4：按任务结构建设 Workflow 与 Agent

### 关注什么

从“判断一个输入”扩展为“完成一个业务任务”，同时控制执行错误。Workflow 适合步骤明确的任务；Agent 适合下一步依赖中间观察、需要动态决策的任务。[2]

### 怎么做

1. 将任务拆成证据获取、判断、动作、结果验证与结束条件。固定步骤优先用 workflow 表达。
2. 将确实需要动态选择的部分交给 Agent，例如决定是否查历史记录、补读图片或升级复核。
3. 为工具定义输入输出、权限、前置条件、错误码、超时和可重试条件。
4. 在 harness 中实现参数校验、状态持久化、幂等、预算、重试上限和结果验证。这里的 harness 指模型之外组织上下文、工具和执行约束的运行系统。
5. 保存任务轨迹：可观察状态、模型动作、工具参数、返回结果、异常、恢复动作和最终业务结果。

例如，客户咨询任务可以固定执行“理解诉求 → 判断是否缺少信息”，再由 Agent 决定是否查询订单、补问办理条件或转人工。对于超时后可能已经成功的处置接口，应先查执行状态，不能无条件重试。

### 产出与验收

产出工具契约、workflow／Agent、可回放轨迹和恢复机制。除最终成功率，还检查错误调用、无效调用、重复动作、预算超限及失败恢复率。

执行系统可通过接口约束消除的错误，应直接修复，不必全部交给模型学习。Agent 评估需要同时看最终结果和轨迹，避免只看答案而漏掉不当操作。[3]

### 何时进入下一阶段

当任务过程可观察、结果可验证，且开始出现重复的经验与失败模式，就可以系统化建设非参数进化。如果失败主要来自接口不稳定，先修接口，不将其误判为智能不足。

</div>

## 七、阶段 5：通过 PE、Memory 与 Skill 实现非参数化进化

### 关注什么

不修改模型权重，将经验转化为可检索、可复用、可验证的行为改进。这条线可以在早期启动，本阶段强调将其建设为稳定机制。

### 步骤 1：让不同经验进入合适的载体

| 载体 | 适合保存的内容 | 必须管理的边界 |
| --- | --- | --- |
| PE | 当前任务的指令、判断方式和输出约束 | 适用范围、模块冲突、上下文长度 |
| Memory | 过去事件、偏好、经验与相关上下文 | 来源、时间、可信度、冲突与过期 |
| Skill | 可复用的任务操作方法 | 触发条件、前置条件、步骤、验证与失败出口 |
| 外置知识与规则 | 业务事实、政策和规范 | 权威来源、生效时间、版本与撤销 |

### 步骤 2：建立候选改进循环

```text
真实失败或重复成功
  → 归因并提出改进假设
  → 生成候选 PE／memory／skill
  → 在开发与诊断数据上优化
  → 在独立留出集和回归集上验证
  → 小流量验证
  → 发布新版本或拒绝候选
  → 监测，必要时回滚
```

提示词和示例的候选搜索可以自动化，DSPy 等工具提供了围绕指标优化程序的实现方式。[4] 但用于反复优化的样本不再是独立测试集，不能用同一批数据同时寻找候选和证明泛化。

### 步骤 3：加入遗忘与淘汰

记忆需要去重、合并、失效和冲突处理；技能需要检查是否过期、冗余或仅对个别样本有效。候选内容不能因为写入成功就自动成为生产规则。

### 产出与验收

产出版本化经验资产、改进记录、评估报告和可回滚发布机制。验收的是后续任务中的成功率、成本、恢复等实际变化，不是反思文字的长度或技能数量。

### 何时进入下一阶段

当业务流程与工具接口相对稳定，已有可验证的高质量轨迹，而模型仍反复出现行为遵循、工具选择或恢复问题，可以考虑 Agent SFT。如果知识检索、提示词或工具修复已能解决瓶颈，无需为了升级而训练。

## 八、阶段 6：Agent SFT 与失败状态纠正学习

### 关注什么

让模型适应真实业务 harness，学会正确操作、停止、升级和恢复。重点不是模仿漂亮的解释，而是学习产生正确状态变化的行为。

### 步骤 1：构建轨迹训练集

轨迹应包含当时可获得的观察、合法工具、选择的动作、工具返回及验证结果。失败状态的纠正答案可以由专家或强模型提出，但必须验证其动作是否有效。

重点覆盖正常完成、正确选工具、参数构造、空结果、超时、证据冲突、部分成功、重复操作风险，以及停止和转人工。失败轨迹要附带纠正目标，不能把错误动作当成成功示范直接模仿。

### 步骤 2：先训练可观察的正确行为

通过 Agent SFT 学习业务格式、工具协议和常见操作序列，分别评估工具调用、结果理解、停止与恢复能力。业务规则经常变化的部分继续外置，不全部固化进权重。

### 步骤 3：用当前模型制造的数据补齐恢复能力

```text
当前 Agent 在受控环境执行
  → 收集它实际进入的失败状态
  → 专家给出纠正动作
  → 验证纠正结果
  → 加入训练数据并更新模型
  → 再次运行，检查新的失败分布
```

这借鉴了 DAgger 的思想：不仅学习专家示范路径，还要在学习者实际访问的状态上获得专家监督。[5] 对 Agent 的应用是工程类比，并不意味着原论文直接证明了所有 LLM Agent 场景的效果。

### 产出与验收

产出适配业务执行环境的模型、失败状态纠正集与分能力评测报告。既检查首次成功率，也检查故障注入条件下的恢复成功率、错误升级率和额外成本。

### 何时进入下一阶段

只有当 SFT 后仍存在多种路径选择、延迟收益或资源分配问题，并且有可靠环境和奖励，才进入 RL。数据量不是唯一门槛；缺少可验证反馈时继续改进监督数据与 harness。

## 九、阶段 7：用 Agent RL 优化业务决策与执行路径

### 关注什么

在业务约束下，提高成功完成任务的概率，并改善工具选择、信息获取、停止和恢复策略。所谓“业务 sense”，需要被翻译为可观察、可验收的决策行为。

### 步骤 1：准备可训练环境

建立可重放、可模拟或可安全试验的环境，明确初始状态、工具行为、任务终止与结果验证。历史轨迹只能提供有限的反事实信息：Agent 选择历史中不存在的动作时，单纯日志回放未必能给出有效结果。

训练环境应覆盖真实故障和业务约束，并保留独立任务、后续时间窗口及生产影子验证，防止策略只适应模拟器。

### 步骤 2：定义约束与奖励

先设置结果正确性、禁止动作和必要验证等约束，再优化成功率、时延、成本和无效调用。不能用节约 token 的收益抵消严重业务错误。

| 希望增强的能力 | 可观察的行为 |
| --- | --- |
| 业务判断 | 依据有效规则完成正确处置 |
| 信息获取 | 缺证据时选择有价值的查询，证据充分时停止 |
| 工具选择 | 选择合法、有效的工具与参数 |
| 失败恢复 | 识别当前状态并采取有效纠正动作 |
| 资源分配 | 将更多预算留给复杂、高代价问题 |
| 路径优化 | 在质量约束下减少无效步骤和重复调用 |

最优路径不必是最短路径。增加一次验证可能降低错误损失，应该按业务总收益判断。

### 步骤 3：训练并检查奖励是否失真

Agent Lightning 等研究提供了 Agent 轨迹与 RL 训练连接、信用分配的实现方向，但业务环境和奖励仍需单独设计。[6]

检查策略是否通过过早结束、回避困难任务、错误声称成功或滥用人工升级获得高分。人工转交可能是正确决策，因此需要同时报告转交率、任务完成率和成本，不能一律奖惩。

### 产出与验收

产出训练后的策略，以及绑定的环境、工具、奖励和评测版本。独立任务上应出现受约束的实际收益，且基础能力不退化；不能只用训练奖励上涨证明业务能力提升。

### 何时进入下一阶段

当部分策略形成稳定、高频的成功路径，可以进入能力再压缩。若训练奖励上升而真实效果不升，应回到奖励、环境和验证器诊断，不持续扩大训练。

## 十、阶段 8：能力再压缩、持续适应与生命周期管理

### 关注什么

将已经探索清楚的能力变成更便宜、更稳定的组件，同时保留发现新问题和处理长尾的能力。

### 怎么做

1. 从经验证的轨迹中识别高频稳定路径，明确其适用前提和失败出口。
2. 根据任务特征沉淀为规则、确定性 workflow、skill、缓存或专用模型，不强行将所有经验都训练进权重。
3. 对固化组件做等价性与边界评测，避免把偶然成功路径固化为普遍策略。
4. 持续监测输入分布、错误类型、升级率、成本和业务规则变化，并抽查自动处理区间。
5. 淘汰过期记忆、技能、规则和模型版本。再训练时加入历史样本回放，检查遗忘；政策确实变化时，显式迁移标签与评估版本。

### 产出与验收

产出能力目录、适用边界、固化组件和漂移报告。成功标准是质量保持、成本或时延改善，并且新问题仍能被发现和升级。

### 如何启动下一轮

```text
业务定义变化 → 返回阶段 0，修订判断契约
新类型与未知错误 → 返回阶段 2，补采样、标注与归因
稳定任务成本偏高 → 返回阶段 3，重新蒸馏与路由
工具或执行状态变化 → 返回阶段 4，修订 harness
经验无法复用 → 返回阶段 5，优化记忆与技能
行为和恢复能力不足 → 返回阶段 6，补纠正数据与训练
策略存在可验证优化空间 → 返回阶段 7，改进 RL
```

整个系统因此形成“探索 → 验证 → 固化 → 压缩 → 发现新问题”的循环。成熟能力可以逐步简化，复杂能力继续由 LLM／Agent 承担。

## 十一、贯穿全程的评估与发布机制

### 1. 使用不同集合回答不同问题

| 集合 | 用途 | 验收原则 |
| --- | --- | --- |
| Baseline 基线集 | 检查简单、明确、应稳定完成的基本能力 | 不退化；必要政策变化需显式迁移契约 |
| Diagnostic 诊断集 | 检查本轮错误假设，包含失败及邻近反例 | 有可解释的专项改善 |
| Challenge 挑战集 | 探索复杂、罕见和多约束边界 | 分析原因，不强求每轮提升 |
| 代表性生产评测集 | 估计真实业务效果 | 按采样设计统计，不用困难集替代 |
| 独立时间留出集 | 检查泛化与近期分布变化 | 不参与提示词搜索或训练 |

挑战集发现难点后，可以建立专项诊断集；专项能力稳定后，再将代表性案例纳入基线集。独立测试数据一旦被用于反复优化，就需要补充新的留出数据。

### 2. 明确指标的分母和业务含义

在本文“需要人工处理为正类”的示例中，误报率为可自动解决的任务中被错误转人工的比例，漏报率为需要人工处理的任务中未被转交的比例。若统计“已转人工任务中不必转交的占比”，应另行命名，避免混用。客户咨询还需单独统计答复错误与诉求遗漏。

同时报告自动处理覆盖率、弃答与升级率、端到端成功率、时延分位数和单任务总成本。Agent 增加错误工具调用率、重复动作率和故障条件下恢复率，并明确各指标分母。

小样本上不能因“零错误”就断言可靠。报告样本量和不确定性；对随机性明显的流程做重复运行，同时评估首次表现与多次运行稳定性。

### 3. 固定实验条件，让改善可以归因

每轮尽量只改变一个主要变量，记录模型、PE、知识库、路由、工具、harness、数据、奖励及推理配置。必要的组合修改应通过分步或消融实验解释贡献。

可以参考同目录的《大模型技能评估实践指南》进一步拆分模型能力、输入质量和上游问题。

### 4. 使用统一发布步骤

1. 写清本轮问题、假设、修改内容与预期收益。
2. 完成标签复核与数据隔离。
3. 通过基线回归、专项诊断和独立验证。
4. 进行影子运行或小流量验证。
5. 根据预先定义的业务门槛扩大流量。
6. 持续观察延迟反馈，异常时回滚到已验证版本。

优化器可以自动提出候选，生产系统应只运行经过验收的版本。发布门槛由业务提前约定，避免看到结果后再调整成功标准。

```text

修改的主要变量：
使用的数据、标签和系统版本：
Baseline 结果：
Diagnostic 结果：
Challenge 发现：
独立评测与代表性生产样本结果：
自动处理覆盖率、误伤、漏放与升级率：
时延、端到端成本及维护投入：
新增风险或退化：
是否满足预先约定的发布门槛：
决定：继续优化／进入下一阶段／扩大使用／回滚
进入下一阶段的具体理由：
仍需保持运行的数据与评估机制：
```

不要用“已积累足够数据”替代进入下一阶段的理由。应说明：哪类能力已经稳定、当前瓶颈是什么、下一种方法为什么能够处理该瓶颈，以及如何验证投入产生了收益。

## 十三、参考资料与适用边界

本文是一套围绕真实业务闭环组织的工程路线，阶段划分及准入条件是综合建议，不是某篇论文已经整体验证的统一流程。以下资料分别支持其中的方法，不构成每个业务都能获得同等收益的保证。

1. [Snorkel: Rapid Training Data Creation with Weak Supervision](https://arxiv.org/abs/1711.10160)：组合有噪声的标注来源，支持冷启动中的弱监督思路。
2. [Anthropic：Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)：区分 workflow 与 Agent，并按任务需求选择系统复杂度。
3. [Anthropic：Demystifying Evals for AI Agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：评估任务结果、轨迹与系统可靠性。
4. [DSPy：Optimizers](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/learn/optimization/optimizers.md)：围绕指标优化提示词、示例或模型参数的工具机制。
5. [DAgger：A Reduction of Imitation Learning and Structured Prediction to No-Regret Online Learning](https://arxiv.org/abs/1011.0686)：在学习者实际访问状态上聚合专家监督，支持失败状态纠正学习的思路。
6. [Agent Lightning: Train ANY AI Agents with Reinforcement Learning](https://arxiv.org/abs/2508.03680)：Agent 与 RL 训练解耦及信用分配的方法参考。
